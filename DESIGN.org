#+TITLE: nexenne design
#+SUBTITLE: how public APIs should feel
#+OPTIONS: toc:2 num:nil ^:nil
#+STARTUP: showall

This file owns nexenne's library design principles: the shape of modules,
headers, errors, examples, and documentation as a user experiences them.
[[file:STYLE_GUIDE.org][STYLE_GUIDE.org]] owns exact C++ syntax and naming mechanics.
[[file:CONTRIBUTING.org][CONTRIBUTING.org]] owns workflow and gates. Prose style
and punctuation live in [[file:doc/writing.org][doc/writing.org]].

North star: a user opens one header and one guide, understands the component,
and can use it without learning the whole repo.

* Public surface

A public component is not finished until the full surface is coherent:

- Header under =modules/<mod>/include/nexenne/<mod>/=.
- Doxygen on every public symbol.
- doctest coverage under =modules/<mod>/tests/=.
- Runnable example under =examples/<mod>/= when public usage changes.
- Guide under =doc/module/<mod>/=.
- Links from the module umbrella header, module CMake, examples CMake, and
  module README where applicable.

The header is the contract, the guide is the explanation, the example is the
first copy-paste, and the tests keep all three honest.

* API shape

- Prefer small types with one clear job over broad configurable machines.
- Prefer values and views over ownership unless ownership is the point.
- Prefer explicit construction and named helpers over implicit conversions.
- Prefer compile-time guarantees when they make the call site clearer.
- Use concepts to state template requirements at the boundary.
- Keep defaults conservative and deterministic.
- Avoid global state. If a component needs state, let the caller own it.

* Error model

Recoverable errors return =std::expected<T, error_t>=. A legitimate absence of
an answer returns =std::optional<T>=. Programmer precondition violations are
documented with =@pre= and can use debug assertions; they are not exceptions in
release.

Each module owns its own error enum when it needs one. Do not create a shared
cross-module error bucket just to avoid naming a local policy.

* Module boundaries

A module should have one reason to exist and a short dependency story.

- =utility= and other foundation modules stay small and dependency-light.
- Data structures belong in =container= unless they are inseparable from a
  higher-level domain.
- Numeric primitives and transforms belong in =math=.
- Spatial primitives and queries belong in =geometry=.
- Random generation belongs in =random= when reproducibility is the promise.
- Build-only or test-only helpers do not leak into public modules without a
  user-facing need.

When a component could live in two modules, choose the lower layer only if the
lower layer can own it without importing domain meaning from above.

* Documentation design

Every guide should answer, in this order:

1. What problem this component solves.
2. The core idea, including invariants and tradeoffs.
3. When to use it and when not to use it.
4. Complexity, allocation, determinism, or threading notes where they matter.
5. A minimal usage example.
6. Further reading for math-heavy or algorithmic techniques.

Do not make the guide a second API reference. Doxygen owns parameter-by-parameter
reference. The guide owns understanding.

* Examples

Examples are small programs, not tests with print statements. They should show
the path a user is likely to copy first. A showcase example can combine several
components, but each public component should still have a narrow example when
its usage is not obvious.

* Performance

Performance claims must name the shape of the cost: complexity, allocation,
branching, determinism, or cache behavior. Do not optimize by weakening the API
contract. When a component exists because it is faster than a standard or common
alternative, document the measured reason or the guarantee the alternative lacks.

* Naming and voice

Names are direct and domain-level. Do not invent synonyms across docs for the
same concept. If the glossary names it =module.deps=, every doc calls it
=module.deps=. If a module calls a failure =invalid_input=, examples and guides
use the same word.

Docs should be plain, technical, and concrete. Avoid sales language and vague
quality words. Say what the API does, what it costs, and what it does not do.
