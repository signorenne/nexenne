This file owns nexenne's project direction. [[file:DESIGN.org][DESIGN.org]] owns how
the public API should feel. [[file:STYLE_GUIDE.org][STYLE_GUIDE.org]] owns C++ mechanics,
formatting, naming, and Doxygen rules. [[file:doc/README.org][doc/README.org]] maps the
rest of the docs.

* The problem

C++ projects grow small local helpers until every codebase has its own vector,
timer, random wrapper, fixed buffer, signal, parser, and test-only utility. Some
of those helpers become reliable. Many stay undocumented, untested, tied to one
application, or hidden behind a build system that makes them hard to reuse.

Large dependency stacks solve part of the problem, but they carry their own
cost: version drift, transitive code, inconsistent error policies, and APIs that
do more than a small project needs. For embedded, simulation, games, and tools,
the sweet spot is often smaller: one focused component, documented well, with
predictable behavior and no surprise runtime.

* The mission

nexenne is a collection of small, focused C++23 modules that can be taken one at
a time or as a whole. A component should be easy to inspect, easy to test, easy
to document, and boring to integrate.

The goal is not to outgrow the standard library. The goal is to fill the gaps
around it: deterministic random distributions, fixed-capacity containers,
stronger utility types, digital filters, math and geometry helpers, signal
dispatch, serialization, and other pieces that benefit from one consistent
style and error policy.

* Core concepts

- /Module/ : one library under =modules/<name>/=, exported as
  =nexenne::<name>= and namespace =nexenne::<name>=.
- /Component/ : one public type, function family, or tight topic inside a
  module. A public component normally has a header, tests, example, and Org
  guide.
- /Dependency layer/ : modules may depend only on lower layers. Dependencies
  live in =module.deps=, one module name per line.
- /Public surface/ : headers, examples, docs, tests, CMake lists, and Doxygen
  comments together define the contract. Code alone is not the whole surface.
- /Guide/ : an Org article under =doc/module/<name>/<topic>.org= that explains
  purpose, idea, usage, gotchas, and references where useful.
- /API reference/ : generated Doxygen from public headers. It complements the
  guides; it does not replace them.

* Principles

1. Standard library first. Use standard facilities unless nexenne needs a
   guarantee they do not provide.
2. One module should be useful alone. A consumer should not need the whole repo
   to take one container, timer, or random engine.
3. Dependencies are explicit and few. A new dependency must earn its place.
4. Determinism beats convenience when behavior matters across platforms.
5. Header-only is the default. Compiled modules are allowed when the design
   actually needs them.
6. Public APIs are small and named plainly. If the concept is hard, the guide
   does the teaching.
7. Tests describe behavior, not implementation.
8. Documentation travels with code. Public API changes update Doxygen, tests,
   examples, and guides together.
9. AI assistance is welcome, but the committer owns every line.

* Non-goals

- Replacing the C++ standard library.
- Becoming a framework that owns an application.
- Adding dependencies to hide small, understandable code.
- Optimizing benchmarks at the cost of undefined or underdocumented behavior.
- Shipping undocumented public APIs.
