#+TITLE: scope_guard
#+OPTIONS: toc:nil num:nil ^:nil
#+STARTUP: showall

* Purpose

=nexenne::utility::scope_guard= is an RAII scope-exit guard that runs its
callable on destruction unless it has been dismissed. It is the commit-or-roll-
back tool: arm a cleanup, do work that might fail, and cancel the cleanup once
success is certain.

* The problem it solves

Many operations build up partial state that must be undone if a later step
fails: rows appended to a log, bytes written to a device, a half-registered
handler, a reservation that has to be returned. Written by hand, the rollback
is duplicated at every failure =return= and skipped on the success path, which
is exactly the shape that rots as the function grows. The usual options each
fall short:

- Rollback code at each failure exit is repeated and easy to forget on a new
  path.
- A success flag checked in a =try= / =catch= handles the throwing path but not
  early returns, and scatters the undo logic.
- [[file:defer.org][defer]] runs cleanup unconditionally, so it cannot express
  "undo only on failure".

=scope_guard= inverts the default: the undo is armed up front and runs on every
exit, and you call =dismiss= at the one point where the work has committed. The
failure paths need no rollback code at all.

* How it works

** The active flag

The guard stores the callable by value plus a =bool m_active= that starts
=true=. The destructor runs the callable only while the guard is active:

#+BEGIN_EXAMPLE
~scope_guard() noexcept(noexcept(m_fn())) { if (m_active) m_fn(); }
#+END_EXAMPLE

=dismiss()= sets the flag to =false= so the destructor skips the callable;
=engage()= sets it back to =true= to re-arm a previously dismissed guard;
=is_active()= reads it. Because cleanup is keyed off a plain flag and not
ownership of a handle, you can toggle it any number of times before scope exit.
The callable is stored by type, not type-erased, so captured lambdas inline
with no =std::function= indirection. The deduction guide
=scope_guard(Fn) -> scope_guard<Fn>= lets you write =scope_guard{[...]{...}}=
without naming the closure.

** Non-copyable, non-movable, and [[nodiscard]]

The guard deletes its copy operations, which also suppresses moves, so it is
bound to the scope where it is declared and cannot be returned or stored. It is
=[[nodiscard]]= so a discarded temporary (which would run cleanup at the end of
the full expression, not at scope exit) is a compile-time warning: name it.

** The construction leak guard

Following P0052, if moving the callable into the member throws, the freshly
armed cleanup must not be lost: the private =guarded_move= invokes it
immediately through the still-intact argument and rethrows, so no guard is left
half-built. The catch path is compiled only when the move can throw.

** The conditionally-noexcept destructor

The destructor is =noexcept(noexcept(m_fn()))=. On a normal scope exit a
throwing cleanup propagates to the caller; if it throws while the destructor
runs during stack unwinding, the program terminates, per the standard
destructor-throws rule. Keep the cleanup non-throwing.

* API tour

- =scope_guard(Fn fn)= : moves =fn= in; the guard starts active.
- =dismiss()= : cancel, so the callable will not run at destruction.
- =engage()= : re-arm a dismissed guard.
- =is_active()= : =true= while armed, =false= after =dismiss=.
- =~scope_guard()= : runs the callable if still active; conditionally =noexcept=.
- =function_type= : the stored callable type =Fn=.

* Usage

Arm the rollback next to the acquisition, run the fallible work, and =dismiss=
only once the operation has committed. Every failure path, early =return= or
exception, runs the rollback for free:

#+BEGIN_SRC cpp
auto const mark{log.size()};
auto rollback{nexenne::utility::scope_guard{[&] { log.resize(mark); }}};

for (int const value : batch) {
  if (value < 0) {
    return false;  // rollback fires here: log shrinks back to mark
  }
  log.push_back(value);
}

rollback.dismiss();  // success: keep the appended rows
return true;
#+END_SRC

* Pitfalls

- *Dismiss on the commit, not before.* If you =dismiss= too early, a later
  failure will not roll back. Call it at the single point where success is
  certain.
- *Throwing cleanup during unwinding terminates.* Same rule as any destructor;
  keep the rollback =noexcept= in practice.
- *Non-copyable and non-movable.* It cannot be returned from a factory or stored
  in a container. To hand off or transfer a cleanup, own a handle with
  [[file:unique_resource.org][unique_resource]] instead.
- *Watch dangling captures.* A =[&]= rollback must only touch state that
  outlives the guard; the guard shares its enclosing scope, so a local captured
  by reference is fine as long as it is declared before the guard.
- *Scope, not statement.* The action fires at the end of the enclosing block, so
  a guard declared inside an =if= runs when that block ends, not sooner.

* Comparison with the standard library

| facility                        | cancel      | owns a value | since   |
|---------------------------------+-------------+--------------+---------|
| =scope_guard= (this)            | yes         | no           | now     |
| =std::experimental::scope_exit= | yes         | no           | LFS v3  |
| [[file:defer.org][defer]] (sibling) | no      | no           | now     |
| [[file:unique_resource.org][unique_resource]] (sibling) | via release | yes | now |

=scope_guard= is the cancellable member of the P0052 scope-guard family and
mirrors =std::experimental::scope_exit=, whose =release()= is spelled =dismiss=
here (with an added =engage= to re-arm). Choose the three siblings by kind:
=scope_guard= runs a cancellable *action* at scope exit, [[file:defer.org][defer]]
runs an *unconditional* action, and [[file:unique_resource.org][unique_resource]]
*owns a handle* and runs a deleter on it, is move-only, and surrenders the
handle with =release=. Rule of thumb: a value to hand off means
=unique_resource=; only code to run at scope exit means =defer= (always) or
=scope_guard= (cancellable).
