#+TITLE: Dependency policy
#+OPTIONS: toc:2 num:nil ^:nil
#+STARTUP: showall

Owns the rules for adding and vetting dependencies. [[file:../AGENTS.org][AGENTS.org]]
carries the one-line floor. This file is the full policy.

Every dependency is a maintenance promise. Add the smallest dependency set that
keeps the library useful, portable, and understandable.

* Current dependency model

- Runtime code depends on the C++23 standard library and nexenne modules listed
  in =module.deps=.
- Tests use doctest, found through =find_package= or fetched by CMake.
- API docs use Doxygen, optionally fetched when missing for local builds.
- CI installs compiler, Doxygen, Graphviz, clang-format, clang-tidy, Ninja, and
  ccache as tooling, not as library dependencies.

* Inter-module dependencies

Use =modules/<mod>/module.deps= for nexenne modules, one module name per line.
That file is the source of truth for build ordering and target linkage.

Do not add a =DEPENDS= argument to a module CMake call for another nexenne
module. Do not duplicate the dependency in the root build.

* External dependency checklist

Before adding a non-standard-library dependency, verify:

1. Necessity: can C++23, a current nexenne module, or a small local component do
   the job clearly?
2. Scope: is the dependency public API, private implementation, test-only, or
   docs/tooling only?
3. Maintenance: recent release, active issue/PR handling, and more than one
   maintainer where possible.
4. Portability: works on GCC, Clang, and MSVC for the supported C++23 surface.
5. License: MIT, Apache-2.0, BSD, ISC, BSL-1.0, or another permissive license
   compatible with MIT. No copyleft or custom terms without maintainer approval.
6. Transitives: list what it pulls in and whether those dependencies are stable.
7. Security: no known unpatched CVEs.
8. Size and compile cost: understand the header weight, generated code, and build
   time impact.
9. ABI: for compiled dependencies, understand versioning and binary compatibility.
10. Escape hatch: document how a consumer avoids the dependency when they do not
    build the module or feature that needs it.

* CMake placement

- Public external dependencies exposed in headers use =LINK_PUBLIC=.
- Private implementation dependencies use =LINK_PRIVATE= and require a compiled
  module kind.
- Test-only dependencies stay in test CMake.
- Tooling dependencies stay in setup docs, scripts, or CI.

Header-only modules cannot hide a private dependency. If a public header includes
it, consumers inherit it, so the bar is higher.

* Standard-library first

Prefer standard facilities before adding a package:

- =<algorithm>=, =<numeric>=, =<ranges>= for traversal and transforms.
- =<type_traits>= and concepts for type logic.
- =<bit>= and =<numbers>= for low-level and numeric helpers.
- =std::expected=, =std::optional=, =std::span=, and =std::string_view= for API
  boundaries.

Re-implement a standard facility only for a stated guarantee: determinism,
=constexpr= support, no allocation, freestanding viability, performance with a
measurement, or a feature the standard does not provide.

* PR requirements

A PR that adds an external dependency must say:

- why the dependency is necessary,
- whether it affects public API,
- license and maintenance status,
- transitive dependency summary,
- which modules and consumers are affected,
- how the change was tested.

If the dependency is only for local tooling or docs, say that clearly so future
reviewers do not treat it as part of the library surface.
